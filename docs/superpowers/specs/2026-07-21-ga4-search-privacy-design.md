# GA4 검색 개인정보 보호 설계

## 1. 목적

장소 검색 행동은 측정하되 사용자가 입력한 검색어 원문은 GA4에 보내지 않는다. 검색 결과가 노출된 횟수, 검색 방식, 결과 수 구간만 수집해 제품 개선에 필요한 신호를 유지하고, GA 향상된 측정이 URL의 `q` 값을 자동 수집하는 경로도 운영 설정에서 차단한다.

## 2. 현재 상태와 문제

- 검색 결과가 확정되면 프런트엔드는 `search` 이벤트를 전송한다.
- 이벤트에는 `search_mode`, `result_count_bucket`만 포함하고 `search_term`은 포함하지 않는다.
- 검색 페이지 URL은 `/search?q=...` 형태가 될 수 있다.
- GA4 향상된 측정의 사이트 검색 기능이 켜져 있으면 코드와 별개로 `view_search_results` 및 `search_term`이 자동 수집될 수 있다.
- GA4 권장 `search` 이벤트는 검색어를 중심으로 정의되어 있어, 검색어를 의도적으로 보내지 않는 현재 명세와 의미가 맞지 않는다.

## 3. 확정된 원칙

- 사용자가 입력한 검색어 원문은 GA4 이벤트, 페이지뷰, URL 필드, 사용자 속성으로 전송하지 않는다.
- 검색어를 해시하거나 일부 마스킹해서 보내지 않는다. 낮은 엔트로피의 장소명은 해시해도 재식별 가능성이 남고 분석 가치도 낮다.
- 검색 결과가 사용자에게 실제로 표시 가능한 상태가 된 뒤 한 번만 이벤트를 보낸다.
- 검색 방식과 결과 수는 현재의 낮은 카디널리티 값만 유지한다.
- 향후 분석 요구가 생겨도 원문 대신 검토된 장소 카테고리나 성공·전환 여부처럼 제한된 파생 신호를 추가한다.

## 4. 접근법 비교와 선택

### 선택: `view_search_results`

현재 `search` 이벤트 이름을 GA4 권장 이벤트인 `view_search_results`로 바꾼다. 이 이벤트는 검색 결과가 사용자에게 제시된 시점이라는 현재 호출 위치와 일치하고, 공식 명세상 `search_term`은 선택 사항이다.

장점:

- 이벤트 이름과 실제 발생 시점이 일치한다.
- 검색어 없이도 GA4 권장 의미를 유지할 수 있다.
- 기존 `search_mode`, `result_count_bucket` 분석을 그대로 이어갈 수 있다.

### 제외: 커스텀 `place_search`

검색어 없는 독자 명세를 가장 명확히 표현하지만, GA4 권장 이벤트와 분리되어 운영자가 별도 의미를 학습해야 한다. 현재 요구에는 추가 유연성이 필요하지 않아 사용하지 않는다.

### 제외: 기존 `search` 유지

코드 변경은 가장 적지만 검색어를 중심으로 정의된 권장 이벤트와 실제 페이로드가 어긋난다. 장기 운영에서 이벤트 의미가 불분명해지므로 사용하지 않는다.

## 5. 이벤트 명세

이벤트 이름은 `view_search_results`이며 다음 두 파라미터만 허용한다.

| 파라미터 | 값 | 설명 |
| --- | --- | --- |
| `search_mode` | `text` \| `map_recenter` | 텍스트 입력 검색 또는 현재 지도 기준 재검색 |
| `result_count_bucket` | `0` \| `1_5` \| `6_20` \| `21_plus` | 검색 결과 개수 구간 |

`search_term`, URL의 `q`, 좌표, 장소명, Place ID는 이벤트 명세에 포함하지 않는다.

## 6. 코드 변경 구조

- `src/lib/analytics/track.ts`
  - `AnalyticsEvents.search`의 실제 값을 `view_search_results`로 변경한다.
  - 타입 키와 호출용 프로퍼티 이름은 기존 호출부 변경을 최소화하기 위해 `search`를 유지한다.
  - 이벤트 파라미터 타입에는 `search_mode`, `result_count_bucket`만 둔다.
- `src/lib/analytics/track.test.ts`
  - 이벤트 스키마 기대값을 `view_search_results`로 변경한다.
  - 검색 이벤트 페이로드 타입이 검색어를 요구하지 않는 구조임을 구현 계획의 타입 검사 단계에서 검증한다.
- `src/app/(main)/search/page.tsx`
  - 현재 검색 성공 시점과 중복 방지 로직을 유지한다.
  - 이벤트 상수를 사용하므로 호출 구조는 바꾸지 않는다.
- `docs/analytics/ga4-operations.md`
  - 향상된 측정의 사이트 검색을 반드시 끈다는 관리자 설정을 추가한다.
  - `q` 데이터 가림은 이중 방어로 유지한다.
  - DebugView와 네트워크 요청에서 `search_term` 및 검색어 원문이 없는지 확인하는 절차를 추가한다.

## 7. 데이터 흐름

1. 사용자가 텍스트 검색 또는 지도 재검색을 실행한다.
2. 검색 요청이 성공하고 결과 데이터가 확정된다.
3. 기존 `searchGeneration` 중복 방지 조건이 같은 검색 실행의 재렌더링을 걸러낸다.
4. 결과 수를 기존 버킷으로 변환한다.
5. `view_search_results`를 `search_mode`, `result_count_bucket`과 함께 전송한다.
6. GA 관리자 설정은 URL의 `q`를 기반으로 한 자동 사이트 검색 이벤트를 생성하지 않는다.

## 8. 운영 설정 책임 경계

향상된 측정 설정은 저장소 코드로 변경할 수 없으므로 운영자가 GA4 웹 데이터 스트림에서 직접 적용한다.

- 관리자 → 데이터 스트림 → 웹 스트림 → 향상된 측정 → 사이트 검색: 끔
- 데이터 가림 대상 쿼리 파라미터의 `q`: 유지
- 변경 후 DebugView에서 수동 `view_search_results`가 한 번만 발생하는지 확인
- `google-analytics.com/g/collect` 요청에서 `search_term`, `q=<원문>`이 없는지 확인

운영 설정이 적용되지 않은 상태를 코드가 감지할 수는 없다. 따라서 배포 체크리스트와 실제 네트워크 검증을 필수 방어선으로 둔다.

## 9. 오류 처리와 개인정보 방어

- 검색 요청 실패 또는 취소 시 이벤트를 보내지 않는다.
- 결과가 0건인 성공 응답은 `result_count_bucket: "0"`으로 측정한다.
- 같은 검색 실행의 재렌더링에서는 이벤트를 다시 보내지 않는다.
- 검색어가 이벤트 객체에 들어갈 수 없도록 이벤트별 TypeScript 파라미터 타입을 유지한다.
- GA 관리자 설정의 URL 데이터 가림은 코드 정규화와 자동 사이트 검색 비활성화가 누락될 때를 위한 보조 방어선으로 취급한다.

## 10. 검증 기준

### 자동 검증

- 분석 이벤트 스키마 테스트에서 `AnalyticsEvents.search`가 `view_search_results`인지 확인한다.
- 분석 관련 단위 테스트가 모두 통과한다.
- TypeScript 타입 검사와 변경 파일 ESLint가 통과한다.
- 전체 테스트에서 기존 검색 및 분석 동작 회귀가 없다.

### 운영 검증

- 텍스트 검색 한 번에 `view_search_results`가 한 번만 발생한다.
- 지도 재검색 한 번에 `view_search_results`가 한 번만 발생한다.
- 0건 검색도 결과 수 버킷과 함께 한 번 기록된다.
- DebugView와 수집 요청에 `search_term`, 검색어 원문, `q` 값이 없다.
- 자동 `view_search_results`와 수동 이벤트의 중복이 없다.

## 11. 범위 제외

- 검색어 원문 또는 해시값 수집
- 검색 UI와 검색 API 동작 변경
- 장소 카테고리 등 새로운 분석 파라미터 추가
- 동의 변경·철회 UI 구현
- 승인 대기 후 `join_group` 보완
- GA 관리자 계정에서의 실제 설정 변경 자동화
